**The analysis (what G3 and the network evidence got right):**
- **E14, Resolver query logs:** the typo'd host NXDOMAIN x2 from inside the VPC (and x6
  with the VPC's search suffix `.ec2.internal` appended).
- **H2 `config-change` CONFIRMED by two checks:** flags deployment #21, 3 min before the
  alarm, still in effect; and `changed-host-resolves`: the host it points at doesn't
  resolve. **H1 `vendor-recs`** confirmed too (40 errors in 5 min). The proposal undoes
  the cause (A1 rolls back #21) rather than working around it (`vendor-fallback-on`).
- **Wrong suspects ruled out with numbers:** valkey (2.1 ms, 0 errors) and DynamoDB
  (5.5 ms, 0 errors). No drift on the cache security group; no network changes; 0
  flow-log REJECTs.
- **Deploys outside the window stay out:** v7/v8 (the S2 drill, 19-21 min earlier) are
  listed as evidence but not blamed, because they're older than the 15-minute window.
- **1 model call** (triage: 1,799 + 158 tokens, $0.00015). The verifier decided by
  checks, with no model. Evidence: 14 items in 7.8 s.

**What viewers saw:** nothing. All 8,097 demo requests in the 45 minutes returned 200:
recommendations fell back to the cached copy (`fallback-on-error`). The incident was
real (a dependency failing for 43 minutes) and invisible to users.

## What the reset found: AppConfig rolled back the fix

The first `./sr demo s4 stop` deployment (#22) was **rolled back by AppConfig after 5
seconds**: *"The following CloudWatch monitors are in alarm:
sr-acme-tv-dev-dependency-errors"*. The rollback monitor on acme-tv's AppConfig
environment is the incident's own alarm. So:

1. **While that alarm fires, every config fix is rolled back**: this reset, the loop's
   own A1 rollback, and `vendor-fallback-on`. S1 never hit it, because S1's alarm
   (latency) isn't the monitor.
2. **The monitor caught nothing on the bad change itself:** #21 completed. The alarm
   needs 2 of 3 one-minute periods, and the bake is 1 minute.
3. **The deploy code reported the rolled-back deployment as live**, because it treated
   `ROLLED_BACK` as a final state. `sr` printed "S4 stopped". An approved A1 would have
   posted "executed" while nothing had changed.

Fixed on 19/11/2026:
- in code: a rolled-back deployment now raises. `sr` exits 1 with AppConfig's reason;
  the loop's Act step fails and escalates "the approved action failed to execute", with
  the reason (tests: `tests/ops/test_opslib.py`, `tests/ops/test_handlers.py`);
- in the design (the owner's decision): **no AppConfig rollback monitor**. The incident
  loop is the rollback path for a bad config ([ADR 0017](../../adr/0017-no-appconfig-rollback-monitor.md)).

The alarm went OK at 15:00:20 only because the traffic had stopped: the same "OK on
missing data" trap as issue #15, used here on purpose to let the reset through.
